# ArenaLine v3.6.0 — Dashboard Refresh & Account Security

## Release purpose

v3.6.0 makes ArenaLine's landing experience match the platform architecture that has emerged through the 3.x line. The general Dashboard is the barn/program operational home; My Team is the IEA-specific team experience. The release also adds self-service verified email changes and optional authenticator-app MFA.

## Dashboard architecture

### General Barn Dashboard

The root `/` dashboard is intentionally ArenaLine-first. It presents permission-aware daily/coming-up activity, action items, operational snapshots, quick actions, and authorized lesson, horse, People, calendar, and finance context.

The general dashboard does not become an IEA dashboard based on a user's Rider, Parent, Coach, committee, or Administrator role. IEA announcements and competition-specific team context remain outside this surface.

### My Team and IEA workspaces

`/my-team/` is the IEA team hub for users related to the team. Parents enter My Team in the parent/family experience first; additional operational responsibilities expose workspace switching without replacing that default.

Authorized IEA workspaces include Coach, Team Parent, Points Secretary, Treasurer/IEA Finance, Show Lead, and Show Manager. Administrators may open every team workspace without changing the semantic distinction between Dashboard and My Team.

### Hero branding

`TeamBranding` now supports a distinct Barn Dashboard hero and focal position in addition to the IEA Team, Futures, and Upper hero assets. Barn presentation prefers the Barn image and falls back to the Team image when none is configured.

Legacy photographic dashboard CSS explicitly excludes the Barn Dashboard hero so the body-level Team hero cannot override the Barn image.

## Account email verification

`UserProfile` stores verification state, a pending replacement email, and the request timestamp.

Email-change behavior:

- requires the user's current password;
- rejects duplicate account email addresses case-insensitively;
- leaves the active email unchanged until verification succeeds;
- uses signed, account-bound verification tokens;
- invalidates stale/replayed requests;
- rolls back pending state when verification mail cannot be sent;
- synchronizes supported legacy contact records after successful verification.

Existing accounts are marked verified by the v3.6 data migration so deployment does not unexpectedly invalidate established users.

## Optional MFA

ArenaLine supports optional TOTP MFA per account.

Enrollment generates a TOTP secret and provides QR/manual authenticator setup. MFA is enabled only after a valid code is confirmed. Eight recovery codes are generated, stored only as hashes, displayed once, and consumed individually.

For MFA-enabled accounts, password authentication establishes a pending challenge rather than a logged-in session. A valid TOTP or unused recovery code completes login. Forced-password-change behavior continues to apply after MFA. Disabling MFA requires the current password and clears the stored MFA secret/recovery material.

## Mail delivery

ArenaLine defaults Django mail delivery to a local Postfix SMTP listener on port 25, with no external SMTP credentials configured by default.

Because ArenaLine runs in Docker, `127.0.0.1` inside the web container refers to that container, not the host. A deployment using host Postfix must provide a safe Docker-to-host route and configure `EMAIL_HOST` accordingly. Postfix must restrict relay access to the intended local/container network.

## Compatibility

- Persisted `Team` remains the organization tenant record behind ArenaLine organization services.
- Existing IEA team dashboards/workflows remain available as specialized workspaces.
- Existing Team/Futures/Upper branding remains valid; Barn hero configuration is additive.
- Existing accounts remain usable after the verification migration.
- MFA is opt-in and does not alter normal login for accounts that have not enabled it.

## Upgrade considerations

Take the normal validated backup before production update. Apply migrations as part of the standard ArenaLine update process. Do not remove or rename already-applied v3.6 migration files solely to make their numeric filenames appear chronological.

The validated v3.6 release candidate was fast-forwarded to `main` after completing the release checklist. Production should deploy the stable `v3.6.0` tag rather than a feature-branch head.
