# ArenaLine v3.1.0 — Public & Live Spectator Experience

ArenaLine v3.1.0 introduces the first deliberate anonymous/public experience while preserving the platform's private-by-default security model.

The release adds public organization/show pages, live multi-ring show status, class-level result publication, spectator notices/delays, a stable live link, and a mobile/tablet Show Day command-center presentation.

## Release principles

v3.1.0 follows four non-negotiable rules:

1. Nothing becomes public merely because it exists internally.
2. Public fields are explicitly allow-listed.
3. Public routes use separate anonymous/public payload services rather than weakening authenticated portal permissions.
4. Publication is reversible without deleting internal show history.

## Public organization and show pages

Organizations may enable a public program profile and deliberately publish selected shows.

Public show controls can expose selected categories including:

- date/time;
- venue/address;
- host/IEA area;
- schedule/class order;
- finalized results;
- live status.

Sensitive internal information remains private by default.

## Live Show Day lifecycle

Show-level lifecycle:

- Ready / Upcoming
- In progress
- Paused
- Complete

Class-level lifecycle:

- Not started
- In progress
- Paused
- Complete

Class state is independent from show state. Completing a class does not complete the show, and pausing a class does not pause the whole show.

## Full show order

Show Day displays every scheduled class even when the organization has no rider entered in that class. Full-team operational roles retain the complete event order, squad-scoped Team Parent roles retain only their permitted Futures/Upper scope, and ordinary family users receive read-only schedule visibility without management controls or hidden rider data.

## Multi-ring operations

v3.1.0 adds structured ring assignment through a companion model instead of rewriting the legacy `ShowClass` schema.

Rules:

- multiple rings may run simultaneously;
- one class may be active/paused in a given ring at a time;
- pausing retains the ring occupancy;
- completing the class frees the ring;
- blank ring assignment uses `Main ring`.

The public page derives all active ring/class states rather than relying on the older single-current-class pointer.

## Class-level result publication

Completed classes may publish/unpublish results independently.

Result publication is not automatic on completion.

Public result payloads expose only approved fields:

- class number/name;
- place;
- rider display name.

They do not expose points-rider designation, points strategy, entry/internal notes, horse medical information, or Finance data.

Public placing badges use ordinal labels (`1st`, `2nd`, `3rd`, etc.) and the established equestrian ribbon-color presentation through 10th place.

## Spectator notices and delays

A separate spectator-safe notice stream is available to Administrator, Coach, and assigned Show Lead users.

Supported operations include:

- whole-show announcements;
- ring-specific announcements;
- break/schedule notices;
- +15 / +30 / +45 / +60 minute ring delays;
- clearing/replacing stale notices.

These notices are separate from family/team communications and become anonymous/public only when the show is published with live status enabled.

## Stable live URL

Each enabled public program has a stable live entry point:

```text
/public/<program-slug>/live/
```

The route redirects to the currently active published show. If no public show is currently in progress/paused, it safely falls back to the public schedule.

This supports reusable QR codes, printed materials, and season-long links.

Highlights:

## Final release gate

Before promotion to `main` and creation of stable tag `v3.1.0`, run:

```bash
./portalctl exec web python manage.py check
./portalctl exec web python manage.py makemigrations portal --check --dry-run
./portalctl exec web python manage.py test portal.tests
```

The complete portal suite must pass on the final release-candidate commit.

Then follow `RELEASE_CHECKLIST.md` for branch comparison, promotion, annotated tag creation, production update, and post-release smoke testing.

## Production update

After the release is promoted and tagged:

```bash
cd /opt/iea-team-portal/app
./portalctl git-status
./portalctl update v3.1.0
./portalctl health
```

Production stable installs follow release tags, not an arbitrary feature-branch head.
