# ArenaLine v3.6.2 — Flexible IEA Lesson Scheduling

v3.6.2 refines the v3.4 Lesson Program architecture for the way IEA teams actually schedule instruction: lesson groups may change from date to date and may include Futures and Upper riders together.

## Scheduling model

For IEA Team Lessons, the individual `LessonOccurrence` is now the primary scheduling unit. `LessonSeries` remains the generic organizational/context container, but an IEA series no longer implies that the same riders meet on a recurring schedule.

The governing rule is:

> **Team membership determines IEA lesson eligibility; the individual lesson occurrence determines who is actually scheduled.**

A rider's `SeasonMembership` still records Futures/Upper membership and determines eligibility for the active season. The scheduled roster is stored explicitly on the occurrence through `IEALessonOccurrenceParticipant`.

New occurrences set `iea_roster_configured=True`, including when the coach intentionally schedules no riders yet. Older occurrences with that flag false retain the v3.4 season/team roster fallback for compatibility.

## Coach workflow

**IEA → Team Lessons → Schedule IEA Lesson** creates a manual occurrence directly. Coaches may set the lesson title, date/time, instructor, location, capacity and notes, then select any eligible combination of Futures and Upper riders.

The roster workspace provides All/Futures/Upper filters and a live selected-rider count. Horse planning is optional and may be revised in the existing lesson-day workflow.

**Schedule Another** prefills lesson logistics but deliberately starts without the prior roster. **Copy Previous Roster** is an explicit action so changing month-to-month groups are never carried forward accidentally.

The Team Lessons page includes a previous/current/next monthly occurrence schedule. Existing converted/legacy lessons remain visible through compatibility surfaces.

## Parent/Guardian Dashboard

The general Dashboard now includes upcoming scheduled lessons for riders linked to the signed-in parent/guardian. Both Barn Lesson Program and IEA Team Lesson occurrences use the same family-facing schedule surface.

Family visibility is relationship-scoped. Parents do not gain access to unrelated riders, staff-only strategy, internal notes, or other private roster information. Past and cancelled occurrences are omitted from the upcoming dashboard schedule.

## Barn lesson compatibility

Barn Lesson Programs are unchanged. They continue to use recurring `LessonSeries`, `LessonEnrollment`, generated/manual occurrences, attendance, assignments, and make-up/move workflows.

The v3.6.2 IEA changes deliberately do not convert Barn scheduling to occurrence-first behavior.

## Legacy compatibility

Already converted historical IEA lessons remain intact. Existing Futures/Upper series created by the legacy conversion are not rewritten solely to match the new scheduling model.

Occurrences created before v3.6.2 may continue using the v3.4 season/team roster fallback. New occurrence-first lessons use explicit occurrence rosters.

## Multi-instance deployment safety

v3.6.2 hardens `portalctl` for servers running more than one ArenaLine installation. `portalctl` now requires `COMPOSE_PROJECT_NAME` in the installation's shared environment file and passes that value explicitly to Docker Compose.

Example production:

```env
COMPOSE_PROJECT_NAME=iea-team-portal
POSTGRES_VOLUME_NAME=iea-team-portal_postgres_data
MEDIA_VOLUME_NAME=iea-team-portal_media_data
```

Example staging:

```env
COMPOSE_PROJECT_NAME=arenaline-staging
POSTGRES_VOLUME_NAME=arenaline-staging_postgres_data
MEDIA_VOLUME_NAME=arenaline-staging_media_data
```

Do not run an ArenaLine installation with an empty or shared `COMPOSE_PROJECT_NAME`. Production and staging must use distinct project names and persistent volume names.

`./portalctl status` is now an explicit alias for the installation-scoped Compose service status.
